Method

Five rules for testing a probe before you spend anything on models.

The negative result is specific to turtle graphics. The framework is not. Every rule below was derived from a failure in this project, and every one of them is checkable in an afternoon with no model access, no API key, and no compute budget.

A capability probe is an instrument. Instruments are usually validated against known inputs before they are pointed at anything unknown — a scale is tared, a thermometer is checked in ice water, a microphone is calibrated against a reference tone. The proposal here is that the same discipline applies to benchmark items, and that the check is cheap enough to be routine.

The five rules below are the checks that would have caught every failure in this project. They are ordered by how early they can be run and how much they cost to run, not by importance.

Rule 1 — Two-door validity

An item is valid only if it is expensive to solve by every cheap route. Enumerate the routes before you guard one.

The design under test guarded a single route: can a small state-free program draw this shape? The test was well built and it worked. It missed the second route entirely — can a small set of absolute actions draw this shape? — because the second route was never considered.

The second door is worse than the first, and not because it is cheaper. It is worse because it leaves no trace in the output statistics. A subject that bypasses a task via a small program still has to find the program, and that shows up as structure in its output. A subject that bypasses via absolute actions simply reads landmarks off the input and jumps between them: the drawing is correct, the metric reports a perfect score, and the mechanism under test was never engaged. There is no signature to detect after the fact.

How to run it

For each candidate item, compute the cost of the intended route and the cost of the cheapest unintended route you can think of. If the unintended route is cheap, the item is dead regardless of how expensive the intended route is. Here, cost was measured as the fewest chords within tolerance of the true path, computed by greedy extension.

In this project the second door killed six of nine shape families on its own — including a regular 199-segment zigzag, drawn by a single absolute move.

Rule 2 — Degeneracy is joint, not intrinsic

"Is this item degenerate?" is not a well-formed question. Degeneracy is a property of the item, the grading tolerance, and the search class together — and you chose two of the three.

A fixed-tolerance test produces a binary verdict. That verdict conceals a decision. In this project the same regular zigzag requires 199 absolute moves at 1% tolerance and 1 at 2%. Nothing about the shape changed between those two measurements. The threshold was the finding.

The same argument applies to the search class. A "valid" verdict from a fitter means "no cheap program found within this class". Widen the class and more items die. In this project a family scored as valid with 54.51% error while being an obvious three-constant closed form that the fitter simply could not represent.

How to report it

Report degeneracy as a function of the threshold, with a table or curve rather than a verdict. Report the search class explicitly, and state the verdict as a lower bound. A reader who sees the curve can disagree with your threshold; a reader who sees "VALID" cannot.

Rule 3 — Prefer scaling over thresholds

Ask whether the required complexity grows with input length. That question is robust to threshold choice. A single number at a single length is not.

This is the only test in the project that is not an artefact of a parameter we selected, and it is correspondingly the only one whose result is unambiguous. The test is simple: fit the item at several lengths and see whether the cost of a compact solution stays flat or grows.

Table 1. The scaling test as a discriminator.
Behaviour of fit cost with N Interpretation Item status
constant the shape has a name degenerate — a subject that knows the name wins at any length
grows with N no fixed program reproduces it candidate — survives this test
cannot be fit at any N no compact form in the search class at all strongest candidate

The result here: the same four parameters draw the spiral whether it has 25 segments or 200. A model that recognises "spiral" reproduces it exactly, at any length, forever. That is a property of the item, not of the model, and no amount of data collection changes it.

Where both a fixed-threshold test and a scaling test are available, report the scaling behaviour as the primary result and the threshold verdict as a footnote.

Rule 4 — Floor-check the measurement

Feed the exact known-correct answer back through the complete pipeline — metric, alignment, normalisation, aggregation — and assert that it scores zero. Run it on every execution and fail loudly.

This rule is not a formality. Four bugs in the measurement code of this project were found by it, and all four had made the headline result look stronger than it was. That direction is not an accident: a bug that flatters your conclusion is the one you have no incentive to hunt.

Table 2. What the floor check caught, and how each bug hid.
Bug Why it did not announce itself
Kinematics derived from a path resampled to equal arc length. Resampling forces every segment to the same length by construction. The step-length sequence was erased and the test silently measured turn angles only. Nothing errored; the numbers just quietly meant something else.
heading -= turn instead of heading += turn. Reproductions were compared against a mirror of the target. The metric is nearest-point, so a mirrored smooth curve still scores well. The bug survived every qualitative inspection.
Alignment returned a centred shape scored against an uncentred original. A constant translation error was added to every measurement — small enough to look like noise, systematic enough to matter.
Unseeded rotation search. For symmetric shapes the search locks onto the wrong symmetry axis — a five-point star is invariant under 72° rotations — and reports a large error for an exact reproduction.

The flagship spiral's measured error went from 3.03% before the fixes to 0.27% after. The headline finding had been understated by a factor of eleven by bugs that made the instrument look better than it was.

What a passing floor check looks like 
FLOOR CHECK -- the exact program must score 0.00%
  spiral (analytic)              0.0000%
  sine wave (analytic)           0.0000%
  ...
  worst floor: 0.0000%  --  PASS

Two practical details. First, the check must exercise the whole pipeline, not the metric in isolation — three of the four bugs above lived in alignment and preprocessing, downstream of the distance function. Second, one bug should get one assertion: a floor check that asserts a single aggregate number catches a single class of bug. Ours asserts per-family.

Rule 5 — Price every required quantity

Enumerate the quantities the item requires the subject to know. For each, ask whether it is locally readable from the input, or recomputable from the subject's own output. If every quantity is one or the other, the item cannot isolate the mechanism it claims to measure — no matter how difficult it is.

This is the rule that produced the fatal finding, and it is the only one of the five that cannot be fixed by better design once it fails. It is also the cheapest to run: it is an argument, not a computation.

Applied here, the enumeration is short. To emit the command for segment k, the subject needs the turn from segment k−1 to segment k. That is the angle between two adjacent pieces of the input image — locally readable. It does not need its own heading, because the simulator maintains that. And where it does need absolute knowledge, it can obtain it by reading a landmark off the image, or by re-summing the tokens it has already emitted.

The general form

If a subject can obtain every quantity it needs from the input it was given, or by re-reading its own output, then the item measures the subject's ability to route information — not the representational format it uses to do so. Difficulty is not evidence of the mechanism.

The five rules applied to this project

Table 3. Each rule, what it found here, and whether the failure was correctable.
Rule Finding Correctable?
1 — Two-door validity 6 of 9 families dead; a regular zigzag drawn by one absolute move Yes — restrict to closed-loop relative-only items
2 — Degeneracy is joint Same zigzag: 199 hops at 1% tolerance, 1 hop at 2% Yes — pre-register the tolerance and report the curve
3 — Prefer scaling 4 parameters fit the spiral at N=25 and at N=200 No — this is a property of the item, not the test
4 — Floor-check 4 bugs, all flattering the conclusion; error understated 11× Yes — fixed, and asserted on every run
5 — Price required quantities Every required quantity is locally readable or recomputable No — this is why the line is closed

Rules 1, 2 and 4 are engineering. They cost an afternoon and they are worth running on any probe, because each of them can save a study. Rule 3 is a property of the item family and cannot be engineered around; it tells you to pick a different family. Rule 5 is a property of the architecture, and when it fails there is no item family left to pick.

Pre-registration: the outcome table

A framework that only tells you an item is bad is half a framework. The other half is committing to what each possible result would mean, before the data exists — because §2 above shows how easily the threshold, and therefore the conclusion, can be chosen after the fact.

For completeness, the conditions and interpretation frozen before any model call in this project. Condition C3 and C5 are the study; the remainder exist so that C3 and C5 can be interpreted.

Table 4. Pre-registered conditions. Not executed — the instrument failed first.
ID Condition Purpose
C0 copy the image fidelity ceiling
C1 describe in words only no-image baseline
C2 reproduce, all commands allowed the naive task
C3 reproduce, relative commands only forces state knowledge
C4 reproduce from a description, no image isolates perception from generation
C5 C3 with output reasoning forbidden isolates hidden state from visible arithmetic
Table 5. Pre-registered interpretation of outcomes.
Observation Interpretation
C3 ≈ C2 and C5 ≈ C3 state knowledge is not the bottleneck; the task measures perception
C3 ≪ C2 absolute commands were carrying the task — narrow finding
C5 ≪ C3 visible arithmetic was carrying the task — models account in their output
C5 ≈ C3, both ≪ C0 the only outcome supporting the original premise
flat across length the length lever does not work; report and stop

Metric and tolerance were fixed in advance: symmetric mean path distance reported together with coverage, at 1% of shape diameter. §2 is the reason this must be frozen before data exists rather than after.

The checklist

The five rules as a list to copy into whatever you are working on. Nothing here requires model access, and the whole sequence is doable in an afternoon.

Table 6. Copy this.
# Check Fail condition
1 List every cheap route to a correct answer. Compute the cost of each. Any unintended route is cheap, or leaves no signature in the output
2 Sweep the grading threshold. Plot the cost of each route against it. The verdict flips within a plausible range of thresholds
3 Fit the item at four or more input lengths. Fit cost is constant in N — the item has a name
4 Feed the exact answer through the whole pipeline. Assert zero. Anything other than zero, or a check that only covers the metric
5 Enumerate required quantities. For each: readable from input, or recomputable from output? Every quantity is one or the other — the item cannot isolate the mechanism
6 Freeze conditions, metric, tolerance and the interpretation table before data exists. Any of the above is still open when the first result arrives

What the framework does not do

It does not tell you whether your probe is a good probe. Passing all five checks means the item is not obviously bypassable, not obviously degenerate, and not obviously measuring the wrong thing. That is a low bar. It filters out instruments that cannot possibly work; it says nothing about whether the survivors measure anything useful.

It also does not replace a power analysis, a sampling plan, or a decision about what effect size would be interesting. Those are the questions you get to ask after the five checks pass, and they are the hard ones.

What it does is move the cheap, decisive failures to the front of the project, where they cost an afternoon instead of a study. In this case, the afternoon's work was the entire contribution.
